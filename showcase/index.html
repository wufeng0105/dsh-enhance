一页读懂 dsh-enhance

给完全没听过它的人准备的读图指南：12 张图按顺序回答 6 个问题——它是什么、插在哪、一条消息怎么走、装与退怎么执行、凭什么相信它、边界在哪。每张图只新增一个概念；不想读长文时，从第 1 张往下看即可。

先读这一段

dsh-enhance 是 DeepSeek Harness 的本地增强件：把「内容边界注入」「审批三态开关」「设置页」做成可开关、可验证、可退出的三件事。它不改宿主代码，只通过 profile patch 里的几行接入；开关与文本住在 <home>/enhance/ 的两个文件里；门禁与负例保证「说的」和「做的」是同一件事；装与卸按行级手术执行，干净路径逐字节还原。

01 · ARCHITECTURE

它插在宿主哪里

enhance 不碰宿主代码：宿主启动时读 profile patch 里的三行 insert 与一个权限替换行，这几行用相对路径指向 <home>/enhance/。

02 · SEQUENCE

一条消息的一生

内容边界不是插件往对话里塞字：宿主装配系统提示时，插件把自己的段落接在末段；证据在会话日志的 system 事件里。

03 · ARCHITECTURE · 数据流

开关与文本只住在这两个文件里

state.json 存三个开关，content-scope.txt 存内容边界；插件每次装配重读，派生结果只有「注入」或「带着原因不注入」。

04 · FLOWCHART

为什么这次没有注入

四道门按顺序问：总开关、内容边界开关、文本非空、文本不超过 8 KB。第一个「否」就是原因，后面的门不再问。

05 · STATE MACHINE

审批三态：拿到请求之后回什么

这个开关不管权限范围，只管 approval/request 递过来之后回什么：allow → allowed-once，ask → 交还宿主，deny → rejected。

06 · PROCESS

门禁与负例：绿不是信，能红才是

六道 fast 门禁串成一条链；绿灯只说明「这次没抓到」。真正证明门禁活着的是负例：在副本上把守卫改回旧写法，它必须变红。

07 · 自定义 · 失败矩阵

失败矩阵：每个坑由谁发现

门禁和设置页检查不是万能的：五行失败形态里，标出来的那一行合并了两条设计边界——没有自动检测，只能人工核对。

已知限制（不假装被覆盖）

  • 宿主档位是 approval: never 时，审批请求根本不发，三态都轮不到。
  • patch 只做行级追加、不解析整份 YAML：结构坏要靠人看。
  • 无 Origin 的请求（curl / CLI）直接放行；接口没有额外 token。
  • 会话探针只读最新一份会话：多工作区并行时可能读错对象。
  • 权限档位有没写进去、写得对不对：设置页检查只看形态，语义要靠人看一眼。
  • 文本上限在写入与读取两侧都生效；超限不注入，设置页检查判红。

自己跑一遍

dsh plugin --profile desktop add github:wufeng0105/dsh-enhance   # 装
node scripts/check.mjs --layer fast                              # 六道门（本机还能核对 DSH 版本）
node scripts/check.mjs --layer full                              # 六道门 + graph-strict
node scripts/check.mjs --self-test                               # 证明每道门都能红
dsh plugin --profile desktop remove dsh-enhance                  # 卸（<home>/enhance/ 的数据保留）
