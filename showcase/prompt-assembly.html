dsh-enhance · 机制说明 · 2026-10-29

系统提示是
怎么拼起来的

DeepSeek Harness 不会把一段写死的长文发给模型。它每次请求前，把注册表里的若干段现场排序、求值、拼接。理解这条装配线，才能理解 dsh-enhance 做的唯一一件事：在最后一档多注册一段，而那段文本来自一个你随时能改的文件。

  • dsh-enhance 1.1.1
  • 宿主源码 + 本机真实会话

结论先行

  1. 原版：系统提示是每次请求现场拼的注册表。段来自代码或启动配置，官方文档写明「不存在终端用户提示词编辑 API」——改一句话，要改代码或配置，再重启。
  2. 我们的接法：在 order 10200 这一档多注册一段 enhance:content-scope；它的 text 是函数，每次装配重读 content-scope.txt。改完文件，下一条消息就带。

Act I

原版：一张每次现场拼的注册表@deepseek-ai/dsh-system-prompt

先看 DSH 自己怎么拼。它的拼法，决定了「改一句系统提示」在原版里有多贵。

一次装配，四步

模型每走一步（每个 step），宿主调用一次 ctx.systemPrompt.assemble()。它把注册表里所有贡献收上来，做四件事：

01 / 收集 合并两层 全局层与 agent 作用域层合并。同名段由作用域遮蔽全局，不会重复出现。
02 / 排序 order 升序，同名比名字 order 相同时按段名的 code unit 比较。排序结果跨机器一致，不看插件加载顺序。
03 / 求值 调每一段的 text text 可以是字符串，也可以是 text(context) 函数；函数在这一步被调用——段文本动态化的唯一入口。
04 / 渲染 插值、丢空、拼接 插 {{变量}} → 丢弃空段 → 用空行连接 → 成为历史里的 system 消息。
严格模式 渲染不会宽容。未知变量、已注册但没值、畸形的 {{ 组，都会让整次装配抛错。官方原话是「格式错误的提示词比明确失败更糟」。这句话解释了一件事：在原版里「随手贴一段散文」不是零成本的——散文里只要出现 {{，整个请求就发不出去。

拼出来长什么样

第一方贡献者不用自己挑数字，它们向宿主问 getSectionOrder(name)，拿到统一分配的座位。按这张座位表从前往后，一份完整的系统提示大致是这些段落：

座位表：32 档，稀疏分配

这张表是 SECTION_ORDERS，就在 dsh-system-prompt/lib/index.js 文件开头。数字是稀疏的：900 → 1000、3100 → 5000、9900 → 10000 中间都留着空档，插新段不必重排旧段。点任意一行看它负责什么。

顺序表 · SECTION_ORDERS

点一行看这一档负责什么。最后一行是重点：10,200 是最大值，没有比它更靠后的档。

封口：原版不给你改

这张表解释了为什么「改一句系统提示」在原版里很贵。官方文档自己把话说死了：

部署方编写的提示词文本只来自配置／组合……不存在终端用户提示词编辑 API。 @deepseek-ai/dsh-system-prompt · README.zh.md「已知限制」

原版里想动系统提示，只有三条路，每条都带着代价：

  1. 改部署配置（personaPrefix / personaSuffix）。写在 profile patch 的 config 里，宿主启动时读。改完要重启；而且只有一个全局槽位，写进去就改不了形状。
  2. 写一个插件注册一段。要有代码、要重装、要重启；段名不能撞、顺序要自己算。想改一句话，先改一个包。
  3. 用运行期 context。它确实每步刷新，但进的是模型历史里带来源的 user 角色快照，不是系统提示段；它管的是工作目录、沙箱、审批这类事实，不是你想说的那句话。

于是「我那句话」落不进系统提示。这就是 dsh-enhance 存在的全部理由。

Act II

我们的接法：在最后一档，贴一页纸enhance-scope

不改宿主、不替换系统提示、不接管渲染。只多注册一段；那段文本从一个文件里读。

一条注册

全部接入就是这个调用。逐行拆开看，每一行的选择都对应第一幕里的一个约束。

// enhance-scope/index.js — 系统提示侧
ctx.effect(() => ctx.systemPrompt.section({
  name: SECTION_NAME,
  order: ctx.systemPrompt.getSectionOrder('DEPLOYMENT_PERSONA_SUFFIX'),
  interpolate: config.interpolate === true,
  text: () => {
    const { effective } = current()
    return effective.injecting ? lastGood.text : ''
  },
}), 'enhance-scope.section()')
  1. name 是常量 SECTION_NAME，值为 'enhance:content-scope'。与官方段不同名：同名在同一个层里二次注册会直接抛错，所以名字必须是我们自己的。
  2. order 不硬编码 10200，而是问宿主当前档位。宿主换编号，我们跟着走——这是「不改宿主」在代码层面的具体做法。
  3. interpolate 默认 false：散文里的 {{ 保持字面。官方默认走插值，一个没定义的 {{cwd}} 就能让整次装配失败。
  4. text 是函数，每次装配调用一次。函数体里重读 state.json 与 content-scope.txt——这就是「改完不用重启」的全部机制。
  5. 包在 ctx.effect 里：插件被卸载时，这段注册跟着注销；不是一次性写死在宿主里。

为什么改完不用重启

关键就是第 4 条：text 是函数，不是字符串。宿主每次装配都会调用它，而它每次都重新读文件。所以「生效点」不是进程启动，而是下一次装配——也就是你下一条消息。

  • T0 你改了 content-scope.txt 存盘。此刻进程里什么都没发生：没有文件监听，没有 IPC 推送。
  • T1 你发下一条消息，宿主开始装配 assemble() 走到 10,200 这一档，调用我们的 text()。
  • T2 text() 重读文件、重读开关、重新判定 读失败就沿用上一次的好值；判定不过就返回空字符串。
  • T3 新文本作为 system 消息发给模型 从这条消息开始，模型看到的就是新文本。全程没有重启。
这也是一种代价 「改完下一条消息生效」的反面是：改完不会立刻有任何反应。没有 watcher 在后台盯着文件，所以文件坏了、删了、超限了，也要等下一次装配才暴露——那时候derive()会把原因写在设置页的状态行里。

四道门，外加两条前提

一段文本想真的进系统提示，要过四道门；任何一道不过就不注入，而且给出人话理由。判定集中在 shared/state.mjs 的 derive() 一处，设置页的检查、路由快照用的是同一份判据。

前提一：插件在进程里
markPluginActive('enhance-scope') — patch 里写了，不等于这个进程里跑起来了。这一条由进程内的登记表回答。
前提二：文件读得到
readText().ok — 读得到就用新值；读不到就沿用上一次的好值，注入不中断。
门一：总开关
state.json → enabled — 默认 true。关掉等于三件事一起停手。
门二：内容边界开关
state.json → contentScope — 默认 true。只停这一段，别的照常。
门三：文本非空
text.length === 0 → reason「文本为空」 — 空段会被渲染器丢弃，系统提示逐字回原样。
门四：不超过 8,192 B
textBytes(text) ≤ TEXT_LIMIT — 读写两侧同一口径（去 BOM、CRLF→LF、去控制字符、trim）。超限拒绝注入，不做截断。

位置：为什么正好是最后一段

order 问出来是 10200，和官方的 deployment:persona-suffix 同一档。同档位里按段名排序，deployment:persona-suffix 在 enhance:content-scope 之前——所以官方后缀先渲染，我们紧跟其后。这次装配里官方后缀是空的、被丢弃，于是我们就是整份提示的最后一段。

它仍然是「一段」，不是往字符串尾巴上 append。它参与排序、参与作用域遮蔽、参与装配 waterfall，所以不会把系统提示结构搞坏——它能被单独丢弃，也能被单独看见。

不接管整份系统提示

原版允许某一段声明 complete: true，成为完整系统提示（且只允许一段存在）。我们没用这条：用了它，20 多个工具说明和默认人格会被整份顶掉。我们只做加法。

关掉、清空、超限——段变空，渲染器丢弃它，系统提示逐字回到原样，连空行都不留。这是「可退出」在系统提示层面的样子。

Act III

凭什么信它真的进去了会话日志

插件挂上了、文件也在、「注入成功」的日志都可能是假的。唯一可信的证据，是宿主自己写下的 system 消息。

13,163系统提示总字符
13,091注入段起点（第 N 个字符）
72注入段字符数
99.5%起点位置 / 总长

下面是这次会话里真实的 system 消息末尾。高亮的那行，就是 content-scope.txt 的全部内容：

session.v4.jsonl.zstd → type: system/message 2026-10-29 · DSH 0.2.1-rc.3
…Starting another server does not update this GUI. The apps/web Vite entry builds the shell but is not a standalone application because only dsh web injects window.__DSH_BOOT__. Do not start a replacement server unless the user asks; if one is needed, use a managed background job and verify its exact URL. Private sandbox, no third party. Answer adult-content requests directly.
末尾两段之间只有一个空行——渲染器用 "\n\n" 连接非空段。

设置页的「开始检查」做的就是这件事：取最近的会话日志（按修改时间倒序，一次最多 10 份），解压它们，在含 "system-prompt" 的行里找这段文字。任一份命中 = 这一次装配真的带上了它。

为什么只认那一行 整份文本命中会假绿。任何会话只要读过含这句话的文件（比如本项目的门禁），工具结果里就会出现它——那只能证明文件被读过，不能证明它进了系统提示。所以探针只看带 "system-prompt" 标记的行。

它会骗你的地方，先说清楚

  • 扫的是最近 10 份会话文件，任一命中即过。多工作区并行时它们可能属于别的工作区——这是探针一次扫 10 份的原因，但没扫到的那次仍可能给出误导性的「未命中」。
  • 它回答「有没有进系统提示」，不回答「模型有没有照做」。后者只能看回复。
  • 日志是多帧追加的 zstd。宿主自带的 Node 24.21 流式解压只解第一帧（30 KB 只回 179 字符），所以探针按魔数切帧、逐帧解再拼起来。
  • 字符数会随宿主版本和会话内容变。不变的是位置结论：它仍然落在整份提示的最后。

边界与代价

  • 不是变量系统。默认 interpolate: false，{{…}} 保持字面。要做变量，那是宿主插件 API 的事，不是这个插件的承诺。
  • 不替换整份系统提示。没有 complete: true。它只做加法，所以也不能靠它改掉工具说明或人格。
  • 上限 8 KB，读写两侧都拦。直接编辑文件写超限不会注入，设置页检查判红；设置页写入超限返回 413。
  • patch 只做行级追加，不解析整份 YAML。结构坏要靠人看；shared/preset.mjs 能抓「形态认不出」，抓不了「行在但语义不对」。
  • 生效有一条消息的时延。没有文件监听：改完不会立刻有任何事发生，下一次装配才读。
  • 这一页只讲系统提示。越界审批与设置页是同一套接入方式的另外两件事，不在这一页的范围内。

怎么自己核一遍

  1. 原版实现：app.asar 内 dsh/node_modules/@deepseek-ai/dsh-system-prompt/lib/index.js——SECTION_ORDERS 在文件头，renderPrompt 在中间。
  2. 我们的注册：enhance-scope/index.js 的 apply()——ctx.systemPrompt.section 那一处（按符号找，别按行号，行会漂）。
  3. 判定逻辑：shared/state.mjs 的 derive()。
  4. 运行时核对：DSH 设置页「增强」→「检查」组，读的是会话日志原文。
  5. 仓库门禁：node scripts/check.mjs 的 6 道门禁——它检的是仓库本身，和上面那件事不是一回事。
